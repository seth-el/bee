# Bounded context status

The ordinary parent/default assistant exposes a read-only `context_status` tool. It is intentionally absent from locked, child, specialist, scout, and other restricted compositions.

The response is structural and quantitative only. Numeric sections mark saturation with `clamped`; source diagnostics mark bounded omission with `sources_truncated`. Tool-facing failures are generic and do not echo arguments, filesystem paths, or underlying diagnostic text:

- `context` keeps two scopes explicit. `budget`, `estimated_used`, and `estimated_remaining` describe the existing `ContextOptions.Budget` over turn-context selection; `request_estimated_used` describes messages in the last provider request attempt. Both use Bee's deterministic `approx_tokens` estimate. A zero budget means the existing unbounded `AssembleContext` convention. Provider tool-definition overhead is not included, and no prompt contents appear in the response.
- `tool_steps` reports provider-tool **batches**, not individual calls: current batch count, configured maximum, and remaining batches. The `context_status` call counts toward the current batch because the loop increments the shared counter before executing calls in that batch. Maximum `0` removes the finite ceiling; the identical completed-batch stall guard remains active in both finite and unlimited modes.
- `dropped` reuses `ContextDiagnostics` counts and projects them into bounded source/count/estimate fields. It has the same `turn_context_selection` scope as the configured budget and does not describe arbitrary provider internals.
- `retrieval` reports configured automatic recall mode, attempted state, one of `off`, `not_attempted`, `success`, `degraded`, or `failure`, and bounded aggregate hit/candidate/returned/source counts for automatic durable-memory and prior-conversation retrieval. Explicit `memory_search` results update the same turn-scoped state without retaining query or result text.
- `plan` reports only existence, a validated plan ID, unresolved-question count, and criterion counts for exactly `pending`, `in_progress`, `passed`, `failed`, and `blocked`. It does not expose goals, prompts, criterion text, evidence summaries, or references.

Before the first provider request attempt there is no request snapshot: `request_snapshot` is `not_available` and `request_estimated_used` is zero. Building or inspecting a request object alone does not create a snapshot. During an active loop, `request_snapshot` is `last_provider_request`; the request estimate describes the messages that produced the current assistant tool batch, before the current tool result is appended. State is reset for each turn and is not written to durable memory or session telemetry beyond ordinary tool-call/result history.
